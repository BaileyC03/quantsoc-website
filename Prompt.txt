<brand-guidelines>
# QuantSoc Brand

## Colours

| Token | Value | Usage |
|:------|:------|:------|
| `--navy` | `#171928` | Primary. The site is navy-first: page background and dominant surface. |
| `--white` | `#FFFEFE` | Primary text on navy. |
| `--white-dim` | `#DFE6EE` | Secondary text on navy, subtle surfaces. |
| `--lime` | `#CED846` | Accent on dark backgrounds: key stats, links, one call-to-action per section. |
| `--lime-dark` | `#BAC73B` | Accent on light backgrounds (non-text only, see below). |

Contrast rules (these override the print brand guide where it's wrong for the web):
- Never lime text on white/light backgrounds. (~1.9:1, fails WCAG.)
- Never white text on a lime background. (~1.6:1, fails WCAG — the brand guide allows it for social posts, the web can't.) Text on lime is always navy (~11:1).
- Lime on navy is ~11:1 and white on navy ~18:1 — both fine for any text size.
- Lime is an accent, not a colour scheme. Use it to point the eye at the single most important thing in a block.
- No light/dark theme toggle. The site is navy. Don't build theming.

## Typography

- Font stack: `font-family: -apple-system, "Helvetica Neue", Helvetica, Arial, sans-serif;`. Helvetica Neue is an Apple system font that can't be freely licensed as a webfont — never import a font file. This also means zero font-loading cost.
- Tracking: the brand guide's "-37" is Illustrator tracking (thousandths of an em). Use `letter-spacing: -0.037em` on headings, `-0.01em` on body. Don't tighten small text further.
- Leading: tight. Headings `line-height: 1.05`, body `1.45`.
- Weight is the hierarchy tool: bold for headings and anything the reader must see first (dates, numbers, venues, CTAs); regular for supporting copy. No italics, no underlines except link hover.

## Logo ("the Quant Swan" — final name TBD, call it "the logo" in code)

Official files are in this folder. All are white/colour artwork on a **transparent** background — they vanish on white, which is why they only ever sit on navy.

| File | What it is | Use it for |
|:-----|:-----------|:-----------|
| `logo.svg` | Vector swan mark alone (it's the "Q"), 1180×1180 viewBox, ~13KB. | Everything on-page: favicon (`<link rel="icon" type="image/svg+xml">`), header mark below 48rem, the Home hero. |
| `longformlogo.svg` | Vector wordmark: "Swansea" / swan-as-Q + "UANT" / "society", 2953×1182 viewBox (2.5:1). | Header at ≥48rem, footer, anywhere the name must be read as the logo. Never narrower than 200px or "Swansea"/"society" become illegible — drop to the square mark instead. **See the text-outline guard below before using.** |
| `logo@2x.png` | 2360×2360 raster of the mark. | Deriving `apple-touch-icon.png` only. |
| `longformlogo@2x.png` | 5906×2364 raster (older composition, no "Swansea" line). | Deriving `og.png` only, and as the on-page longform fallback if the SVG fails the guard. |

Text-outline guard: `longformlogo.svg` as supplied contains live `<text>` in `HelveticaNeue-Bold`. Browsers without that font (Windows, Android, Linux) substitute Arial/Roboto and the wordmark shifts. Before using it, run `grep -c '<text' longformlogo.svg` — it must print `0`. If it doesn't, use `longformlogo@2x.png` for the longform and tell the user to re-export the SVG with text converted to curves. Don't try to fix the SVG yourself. (`logo.svg` has no text and passes.)

Rules:
- Only on navy. On a light section, give it a navy backing panel.
- Never stretch, crop, trim, recolour (the wing may change colour for Halloween/Pride only), show partially, or add elements to it. Keep the files' built-in padding; don't add much more.
- SVGs go in `src/assets/` and are used with a plain `<img>` (import the file for the `src`) with explicit `width`/`height` matching the viewBox ratio. They don't go through `<Image>` — nothing to optimise, they're already smaller than any raster and crisp at every size. If a PNG ends up on-page (fallback case), it goes through `<Image>` as WebP/AVIF *with alpha* — never JPEG.
- Alt text: `"Swansea Quant Society"` when the logo is the header link; `alt=""` when it's decorative beside a text heading. Don't also put the name in text next to the longform — it already says it.
- `apple-touch-icon.png` (180px, from `logo@2x.png`, on a navy square — iOS doesn't support SVG or transparency here) and `og.png` (1200×630, navy, `longformlogo@2x.png` centred) are generated once with one ImageMagick/sharp command and committed to `public/`. No build-time image generator.

<stack>
# Stack: Astro, static output, plain CSS

Why Astro: file-based routing and one shared layout for five pages, ships zero JS by default, built-in `<Image>` produces WebP/AVIF with width/height for free, `astro build` emits plain static files for any free host, and it's built on Vite — so three.js later is `npm i three` plus a `<script>` tag on one page, which Astro bundles and code-splits per page automatically. Nothing else on the list does all of that without extra dependencies.

Use:
- Astro latest, `minimal` template, default `output: 'static'`.
- Plain CSS with the custom properties above in one `global.css`. No Tailwind, no preprocessor.
- `astro:assets` `<Image>` for every raster image.

Do not add: React/Vue/Svelte integrations, Tailwind, a UI kit, an animation library, MDX or content collections (content is hardcoded), view transitions/client router, a CMS, a database, auth, analytics scripts, a theming system.

## Future three.js (do not build now)

The stack is chosen so this is a small additive change later:
- `npm i three`; import inside a `<script>` in the one page/component that needs it. Never React Three Fiber (drags in React).
- Load it after first paint on that page only (dynamic `import()` on idle or when the canvas scrolls into view). The static page must be complete and LCP-ready without it.
- Static poster image as fallback; skip the scene under `prefers-reduced-motion`.
- The <100KB initial-JS budget below excludes the deferred 3D chunk; everything else still has to fit.
</stack>

<constraints>
# Performance, maintenance, and clean code

Performance bar — verify before calling anything done:
- Lighthouse Performance ≥ 95 on mobile, LCP < 2.0s, CLS < 0.05.
- Initial JS < 100KB gzipped per page. Expected: ~0KB — a brochure site needs no client JS. CSS transitions cover hover states.
- Every image via `<Image>` (WebP/AVIF, explicit dimensions), `loading="lazy"` below the fold. Hero/logo eager.
- No webfont, no third-party scripts, no external requests except the two outbound links.

Responsive — the site must work at every width from 320px to ultrawide, mobile first:
- `<meta name="viewport" content="width=device-width, initial-scale=1">` in the layout. Never disable zoom.
- Write mobile styles as the default; add `@media (min-width: 48rem)` and `(min-width: 64rem)` only where a layout actually changes. No other breakpoints.
- Fluid type: `clamp()` for headings (e.g. `font-size: clamp(2rem, 6vw, 4rem)`), body never below 16px. Tight tracking/leading from the brand must still be readable at the smallest size.
- Fluid layout: content column `max-width: 72rem; margin-inline: auto; padding-inline: clamp(1rem, 4vw, 2.5rem)`. Grids use `repeat(auto-fit, minmax(16rem, 1fr))` so cards reflow without breakpoints. No fixed pixel widths on anything.
- Images: `max-width: 100%; height: auto`. Logo and OG image have an explicit aspect ratio so they never distort.
- Nav: the five links wrap onto two lines on narrow screens (`flex-wrap`), still 44px tall each. Don't hide them behind a JS hamburger.
- Touch targets ≥ 44×44px; adjacent links have ≥ 8px gap.
- No horizontal scroll at any width; long words/URLs get `overflow-wrap: anywhere`.
- Reflow test: at 320px CSS width (which is also 200% browser zoom on a 640px window) everything is readable in one column with no clipping.

Maintenance ("set and forget"):
- All content is hardcoded in the page files. Editing copy = editing one `.astro` file.
- Anything that changes often (events, sign-ups) links out to LinkedIn / SU. No on-site equivalents.
- No dependency that needs patching, renewing or paying for. `astro` and `three` (later) are the whole dependency list.
- Static host only (GitHub Pages / Cloudflare Pages / Netlify — any free tier). No server, no env vars, no build secrets.
- The repo belongs in a society-owned GitHub org, not a personal account. Committee turnover is how society sites die. Put handover steps (where hosting lives, how to change copy, how to rebuild) in the README.

Clean code — apply this ladder to every decision, stop at the first rung that holds:
1. Does it need to exist? Five static pages don't need routing libs, state, a component library, a token pipeline, or "for later" scaffolding. Skip speculative work and say so in one line.
2. Does HTML/CSS already do it? `<details>` for accordions, CSS grid/`:hover`/`scroll-behavior` over JS, native lazy loading over a library.
3. A dependency has to replace real work, not a few lines of CSS. Justify any addition in one line.
4. No abstractions with one call site, no config for values that never change, no wrapper components "for consistency". Use the CSS variables directly.
5. Fewest files, fewest concepts. Boring markup a first-year can edit beats a clever pattern that needs a comment.

If a step seems to want something heavier (a CMS, admin panel, animation system), ship the lean version that meets the actual requirement and note in one line what was skipped and what would justify it. Don't build it pre-emptively, don't stall asking.
</constraints>

# Steps (do them in order; each has a done-check)
